# Architecture  
Event Queue Framework – VSDSquadron Mini

This document describes the **system architecture** of the Task-4 embedded project, focusing on **structure, data flow, and design decisions**.

---

## High-Level Architecture

The system follows an **event-driven architecture** with clear separation between:

- Hardware drivers
- Event management
- Application logic

```
+---------------------+
|   Application       |
|     (main.c)        |
+----------+----------+
           |
           v
+---------------------+
|   Event Dispatcher  |
|  (event_get_next)   |
+----------+----------+
           |
           v
+---------------------+
|   Event Queue       |
| (FIFO-based buffer) |
+----------+----------+
           ^
           |
+----------+----------+
| Event Producers     |
| - Timer Logic       |
| - LED Requests      |
+---------------------+
           |
           v
+---------------------+
|   Drivers Layer     |
| GPIO | UART | Timer |
+---------------------+
           |
           v
+---------------------+
|   Hardware          |
| VSDSquadron Mini    |
+---------------------+
```

---

## Layered Design

### 1. Driver Layer
Lowest level of the system.

- GPIO driver controls LED hardware
- UART driver handles serial communication
- Timer logic provides base time reference

**No application logic exists in this layer.**

---

### 2. Event Queue Layer
Middle abstraction layer.

Responsibilities:
- Store events generated by producers
- Provide FIFO-based retrieval
- Decouple timing between producers and consumers

This layer behaves like a **software message buffer**.

---

### 3. Application Layer
Top-level logic in `main.c`.

Responsibilities:
- Generate events
- Dispatch events
- Decide application behavior

**No direct register access is allowed here.**

---

## Event Flow

1. Application generates events based on timing
2. Events are pushed into the event queue
3. Dispatcher periodically fetches events
4. Events trigger actions (LED toggle, UART logs)

```
Producer → Queue → Dispatcher → Driver → Hardware
```

---

## Control Flow vs Data Flow

### Control Flow
- Determined by the main loop timing
- Dispatcher runs slower than producers

### Data Flow
- Event objects passed through queue
- UART logs mirror internal state transitions

---

## Why Event-Driven Architecture?

This architecture was chosen because:

- It mirrors **real embedded OS designs**
- Separates *what happens* from *when it happens*
- Makes system scalable and testable
- Maps cleanly to digital hardware concepts

---

## Relation to OS and Computer Architecture

This design reflects:

| OS Concept | Implementation |
|----------|----------------|
| Scheduler | Dispatcher loop |
| IPC | Event queue |
| ISR abstraction | Event producers |
| Task separation | Producers vs consumers |

## Hardware Mapping

- LED: GPIO PD5
- UART: Debug UART via WCH-Link
- Clock: SystemCoreClockUpdate()
